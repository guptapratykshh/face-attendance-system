2. Executive Summary & Problem Statement

2.1 Problem Statement

Schools, offices, and small workplaces still mark attendance with paper registers, shared PINs, RFID cards, or a mobile “I am here” button. These methods are easy to share, easy to fake, and hard to audit. A person can mark a friend present, punch from home, or lose a card.

A face attendance system can replace that ritual with a camera: the person looks at the device, the system recognises an enrolled face, and a present/absent record is stored. That only works if three things are true:

  1. The face on camera is matched to the correct enrolled person (identity).
  2. The capture is a live person, not a printed photo or a phone screen (liveness).
  3. Staff can see and export who was present, without running a research notebook.

Existing consumer “face unlock” is built for one device and one user. Workplace attendance needs a gallery of many people, a web dashboard, accounts, and a REST API. Off-the-shelf attendance products are expensive, closed, and rarely expose how the model was evaluated. This project builds a small, inspectable full-stack system: React UI + FastAPI + a published face encoder, with accuracy reported on a public benchmark (LFW).

2.2 Project Objectives

Technical / functional goals (initial product)

  1. Enroll people with face photos and store a searchable embedding gallery.
  2. Let an employee or kiosk camera check in; mark present only on a confident match.
  3. Provide login (admin vs employee), people CRUD, an attendance dashboard, and CSV reports.
  4. Fuse two streams for a check-in decision: face appearance (who) and a short blink / motion cue (alive).
  5. Expose the same behaviour through a documented REST API.

Success metrics (grading + product)

Metric Initial target
Dashboard load < 2 s on a normal laptop / campus Wi‑Fi
Authentication JWT sessions; passwords hashed; role-restricted routes
CRUD accuracy Create / read / update / deactivate a person and see the change on the dashboard
Report generation Date-range attendance export as CSV (PDF optional in Month 3)
UI Responsive web layout (desktop + phone browser)
Recognition TAR@FAR = 1e-3 reported on LFW View 2; operating threshold taken from that curve
Check-in latency Face detect + embed + match typically < 1 s on CPU for one face

Audience and impact

  • Employees: mark presence without a shared PIN.
  • Administrators / HR: one screen for today’s present list and a downloadable register.
  • Security / reception: a simple camera check-in page.
  • Practical impact: fewer proxy punches, a stored audit trail, and a student-built system whose model quality is measurable — not a black-box demo.

3. System Architecture & High-Level Design

3.1 End-to-End System Pipeline

User journey (check-in)
Employee or staff opens the web app → signs in → camera captures a frame (and a short burst if liveness is on) → backend runs the vision pipeline → identity + liveness decision → attendance row written → dashboard refreshes.

Data ingestion

  • Sources: webcam JPEG/PNG from the browser; admin-uploaded enrollment photos; public LFW images for offline model evaluation only (not mixed into the live gallery).
  • Mode: request/response (not a Kafka-style stream). Each check-in is one HTTP call (or a small burst of frames for blink).
  • Raw formats: RGB images; metadata = user id, timestamp, optional site label.

Processing & modeling engine

  1. Detect face (SCRFD). Reject: no face, several faces, face too small / blurry.
  2. Align with 5-point landmarks (similarity transform) to a fixed crop.
  3. Embed with FaceNet or ArcFace → L2-normalised 512-D vector.
  4. Match cosine similarity against the in-memory gallery (FAISS IndexFlatIP or equivalent exact inner product).
  5. Liveness (multimodal stream 2): eye-openness over a short frame sequence; require a blink-like valley so a still photo is less likely to pass.
  6. Decision: present if similarity ≥ threshold and liveness passes (when enabled); otherwise no_match / failed and no attendance credit.

Storage layer

  • SQLite (dev) / PostgreSQL (deploy): users, people, embeddings metadata, attendance rows, events.
  • FAISS (or numpy cosine) index in process memory, rebuilt from stored embeddings.
  • Files: model weights (weights/), evaluation JSON (reports/evaluation.json).

Presentation layer

  • React + Vite SPA (Tailwind CSS): login, check-in, people directory, today dashboard, reports.
  • FastAPI REST under /api/v1.

5. Functional & Non-Functional Requirements

5.1 Functional Requirements

Feature 1 — Core attendance module (web)

Users Employee (self check-in); Admin (directory + dashboard)
Input Webcam frame(s) after login; or admin-uploaded enrollment photos
Behaviour If the face matches an enrolled person above threshold (and liveness if on), write present for today with timestamp. Duplicate check-in the same morning updates time or is ignored (single daily present for v1).
Output On-screen name + time, or a clear error: no face / unknown / try again. Admin Today view lists present vs not yet in.

People CRUD: admin can add name + employee id, upload 1–5 enrollment photos, deactivate a person (they must not match after deactivation).

Reports: filter by day / week / month; Export CSV (required). PDF export is a Month 3 polish item, not a Viva 1 blocker.

Feature 2 — API layer

Prefix: /api/v1. JSON + multipart/form-data for images. Auth: Authorization: Bearer <JWT>.

Method Path Purpose
POST /auth/login Username + password → access token
GET /auth/me Current user + linked person
GET/POST/PATCH /persons Directory CRUD (admin)
POST /persons/{id}/enroll Upload enrollment image(s)
POST /attendance/check-in Webcam image → present / reject
GET /attendance List records (role-filtered)
GET /attendance/export CSV download
POST /verify Lab: two images → similarity (admin/operator)
GET /health Encoder name, gallery size, thresholds

Typical check-in payload: image file. Response: { decision, person_id, name, similarity } or HTTP 4xx with detail (no_face, no_match, liveness_failed).

Feature 3 — Model inferencing

  • Realtime: one request, one (or a short burst of) frame(s); no overnight batch jobs for v1.
  • Offline batch: LFW evaluation scripts (scripts/evaluate.py) to pick encoder and threshold.
  • Gallery: embeddings stored at enroll time; check-in only computes the probe embedding.

5.2 Non-Functional Requirements

  • Performance & latency: dashboard shell < 2 s; single-face inference target < 1 s on CPU (ArcFace ONNX). Not a 200 ms GPU SLA — that is unrealistic on student hardware.
  • Scalability & concurrency: v1 sized for one workplace / one class (tens to low hundreds of identities, a few simultaneous check-ins). Not a city-scale cluster.
  • Security & privacy: bcrypt/argon2 hashes; JWT expiry; HTTPS on deploy; enrollment photos stored only for enrolled staff; no public gallery dump. Consent: organisation informs people that faces are used for attendance.
  • Reliability: reject bad frames instead of guessing; log failed checks; if the encoder cannot load, /health reports error and check-in returns 503.

6. Data Strategy & Management

Dataset source & acquisition

  • Live product data: enrollment photos captured on site (not scraped).
  • Benchmark: LFW (Huang et al.) — unrestricted View 2 pairs for TAR@FAR. Optional small VGGFace2 subset only for optional FaceNet fine-tune (Month 2), with LFW-overlapping identities excluded so test is not contaminated.
  • The track spreadsheet lists WikiQA / RAG; those belong to NLP/Gen-AI tracks. This project is vision, so LFW is the evaluation set.

Preprocessing & cleaning

  • Detect → 5-point align → resize (160 FaceNet / 112 ArcFace) → RGB uint8.
  • Drop frames with no face, multiple faces, or weak detection score.
  • Embeddings L2-normalised; score = cosine (inner product of unit vectors).

Privacy & compliance

  • Face images are biometric-class data: keep them on the organisation’s server; do not publish student webcam captures.
  • Provide admin deactivate / delete person so a leaver can be removed from the gallery.
  • Evaluation uses public LFW only.

Data version control

  • Code + this PRD on GitHub (from 6 Sept).
  • Weights via documented download URLs / Git LFS if required; do not commit raw LFW if the licence forbids redistribution — scripts download it.
  • reports/evaluation.json versioned so the API threshold is reproducible.

7.4 Track D: Multimodal AI

Multimodal data fusion

Two streams at check-in:

Stream Modality What it answers
A — appearance Single RGB face crop Who is this? (embedding + gallery cosine)
B — temporal liveness Short burst of frames (eye-openness / blink) Is this a live person or a still photo?

Fusion strategy (v1): late fusion. Each stream produces its own decision (identity_ok, live_ok). Attendance is granted only if both pass. We do not train a cross-attention vision-language transformer for v1 (overkill and slow on CPU). Early pixel fusion is not used because blink is a time signal, not a second camera.

This is multimodal in the OJT sense: spatial identity + temporal motion, not text+image RAG.

Model architecture

RGB frame(s)
    ├─► SCRFD detector ─► 5-pt align ─► ArcFace/FaceNet encoder ─► 512-D embedding
    │                                                      └─► cosine vs gallery ─► identity_ok
    └─► eye-crop sequence (from landmarks) ─► blink / openness heuristic ─► live_ok

late AND  →  mark present
  • Identity encoder: InsightFace ArcFace w600k_r50 (ResNet-50) as the default served model if it wins TAR@FAR; FaceNet Inception-ResNet-v1 as baseline comparison.
  • Detector: SCRFD-10GF (not MTCNN-only).
  • No CLIP / ViLT in the initial PRD.

Domain references (Computer Vision)

  1. Schroff, Kalenichenko, Philbin. FaceNet: A Unified Embedding for Face Recognition and Clustering. CVPR 2015.
  2. Deng, Guo, Xue, Zafeiriou. ArcFace: Additive Angular Margin Loss for Deep Face Recognition. CVPR 2019.
  3. Huang et al. Labeled Faces in the Wild (dataset / protocol).
  4. (Liveness) treat printed-photo / screen replay as the spoof class; v1 uses a challenge blink plus simple texture/freeze cues — not a certified ISO PAD product.

Explainable AI (XAI) & latency

v1 (must have)

  • Show similarity score and matched name on success.
  • Show a reason code on failure (no_face, multiple_faces, below_threshold, liveness_failed).
  • Operator lab page (Month 2): verify two photos and see the cosine — a simple explanation of “why match / why not”.

Month 3 (stretch, not required for PRD approval)

  • Overlay detection box + landmarks on the captured frame.
  • Optional Grad-CAM on the aligned crop for a lab screenshot in the demo video.

Latency

  • Keep gallery exact cosine (no ANN) while N is small.
  • ONNX Runtime on CPU; avoid loading two heavy encoders in one process.
  • Dashboard data from SQL aggregates, not by re-running the model.

8. Testing, QA & Validation Strategy

Unit & integration testing

  • Pytest for API contracts: login, enroll, check-in decision shape, CSV export, role 403s.
  • Frontend: a small Vitest/React Testing Library set for login and dashboard rendering.
  • Fake encoder in CI so tests do not download ArcFace weights.

Model validation & benchmarks

  • LFW View 2: 10-fold accuracy; TAR at FAR = 1e-2, 1e-3, 1e-4.
  • Serve the encoder with the best TAR@FAR = 1e-3.
  • Adversarial / spoof: still-photo burst must fail blink; frozen identical frames must not count as live (Month 2 tests).
  • Data leakage: training identities must not overlap LFW when any fine-tune is attempted.

Edge cases

Input Expected behaviour
No face / too dark Reject; tell user to face the camera
Two people in frame Reject (do not guess)
Unknown visitor no_match; not marked present
Deactivated person Must not match
Camera permission denied UI error; no silent fake success
API down Frontend error state; no corrupted attendance row

Appendix B — Model card (outline for Month 3)

  • Input: aligned RGB face crop.
  • Output: 512-D unit embedding.
  • Decision: cosine ≥ τ from LFW FAR = 1e-3 and liveness pass.
  • Limitations: lighting, masks, large pose, lookalikes, non-certified anti-spoof.
  • Ethics: use only with workplace/school notice; delete embeddings when a person leaves.
